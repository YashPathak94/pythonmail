Helm to Argo CD Migration — End-to-End Implementation and Rollout Plan
PROJECT PROPOSAL | MANAGEMENT REVIEW | VERSION 1.0

Project: Migration from Jenkins-driven Helm deployments to Argo CD GitOps
Platform: AWS EKS | Jenkins | Helm | Argo CD | Git | AWS ECR
Scope: DEV → INTG → ACCP → PROD → DR
Deployment strategy: One namespace at a time, with validation and rollback checkpoints
Proposed start: 12 October 2026

1. Executive summary
The objective is to migrate the existing Jenkins-based Helm deployment process to an Argo CD GitOps-based deployment model without rebuilding the current Helm charts, disrupting existing applications, or introducing unnecessary production risk.

Under the proposed approach:

Jenkins remains responsible for CI: package builds, Docker image builds, security scans, publishing artifacts, and updating deployment versions in Git.

Argo CD becomes responsible for CD: reconciling the approved Git configuration with the Kubernetes cluster, deploying applications, monitoring synchronization, and identifying drift.

Existing Helm templates and environment-specific values.yaml files will be reused, with adjustments where required for Argo CD compatibility.

Each namespace will be migrated independently, starting with DEV, followed by DEVB, DEVC, integration environments, acceptance, production, and disaster recovery.

Existing Jenkins/Helm deployment capability will be retained as a tested fallback during each namespace's stabilization period.

The implementation will use a controlled, phased migration with explicit go/no-go approvals before progressing to higher environments.

Example Argo CD Application manifest
This example assumes a Git repository containing the existing microservice Helm chart and namespace-specific values.


apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: customer-api-devb
  namespace: argocd
spec:
  project: nonprod
  source:
    repoURL: https://git.example.com/platform/gitops.git
    targetRevision: main
    path: charts/microservices
    helm:
      releaseName: customer-api
      valueFiles:
        - ../../environments/dev/devb/customer-api.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: customer-services
  syncPolicy:
    syncOptions:
      - PruneLast=true

The chart path, environment values path and namespace are illustrative. The relative values-file location must be validated against the selected repository layout and the Argo CD version.

The configuration intentionally has no automated sync policy. This is the safer initial state for existing-resource adoption and production migration.

Example Jenkins pipeline — GitOps promotion
This pipeline illustrates the new deployment stage, assuming the application has already been migrated to Argo CD and its image has been built and pushed.


pipeline {
  agent any

  parameters {
    choice(
      name: 'ENVIRONMENT',
      choices: ['dev', 'devb', 'devc',
                'intg', 'intgb', 'intgc',
                'accp', 'proda', 'prodb', 'dr']
    )
    string(name: 'SERVICE', defaultValue: 'customer-api')
    string(name: 'IMAGE_TAG', defaultValue: '')
  }

  stages {
    stage('Validate') {
      steps {
        sh '''
          test -n "${IMAGE_TAG}"
          echo "Deploying ${SERVICE} to ${ENVIRONMENT}"
        '''
      }
    }

    stage('Update GitOps Repo') {
      steps {
        git(
          url: 'https://git.example.com/platform/gitops.git',
          credentialsId: 'gitops-write',
          branch: 'main'
        )

        sh '''
          set -e
          FILE="environments/${ENVIRONMENT}/${SERVICE}.yaml"

          test -f "$FILE"

          # Assumes image.tag is a field in this values file.
          export FILE IMAGE_TAG
          yq -i '.image.tag = strenv(IMAGE_TAG)' "$FILE"

          git config user.name "jenkins-gitops"
          git config user.email "jenkins@example.com"
          git add "$FILE"

          if ! git diff --cached --quiet; then
            git commit -m "Promote ${SERVICE} to ${IMAGE_TAG}"
            git push origin HEAD:main
          fi
        '''
      }
    }

    stage('Wait for Argo CD') {
      steps {
        withCredentials([
          string(
            credentialsId: 'argocd-token',
            variable: 'ARGOCD_AUTH_TOKEN'
          )
        ]) {
          sh '''
            set -e
            export ARGOCD_SERVER="argocd.example.com"

            APP="${SERVICE}-${ENVIRONMENT}"

            # Required for manually synchronized applications.
            argocd app sync "$APP" --timeout 600
            argocd app wait "$APP" \
              --sync --health --timeout 600
          '''
        }
      }
    }
  }

  post {
    success {
      echo 'Argo CD deployment completed successfully.'
    }
    failure {
      echo 'Deployment failed; initiate the approved recovery runbook.'
    }
  }
}
Production hardening before use: The example deliberately omits image build stages and advanced release controls. In the actual implementation, Jenkins should use a protected promotion branch/PR, exact commit verification, per-environment credential scope, immutable image digests, approval gates, and an application-level smoke test. A shared main branch plus direct push is suitable only for an appropriately controlled proof of concept.

Argo CD officially supports this CI integration model, including synchronization and waiting for the application to reach the desired state.

7. Rollback and recovery plan
Rollback will be designed at two separate levels:

Application release rollback: Return an Argo CD-managed application to its previously approved Git configuration.

Migration rollback: Return the namespace to the legacy Jenkins/Helm deployment mechanism when the Argo CD adoption itself creates a problem.

These are not the same operation and must have separate tested procedures.

A. Application-level rollback
Deployment failure detected

Health degradation / functional failure / release rejection

Stop new deployments

Freeze target app, namespace and release promotions

Restore last-known-good Git state

Revert failed change; verify dependencies and image availability

Argo CD sync

Apply restored desired configuration

Validate recovery

Health • Endpoints • Error rate • Logs • Business transactions

A basic recovery command sequence for an approved Git revision revert could be:

# Revert the offending GitOps configuration commit
git revert <failed-commit-sha>
git push origin main

# With an appropriate Argo CD session/token
argocd app sync customer-api-devb

argocd app wait customer-api-devb \
  --sync --health --timeout 600

The Git revert must be reviewed and contain only the intended changes. In an approval-based environment, use a pull request rather than directly pushing to the protected branch.

Argo CD's documented behavior is important here: its historical rollback operation is not available while automated synchronization is enabled. Git revert and reconciliation is the preferred GitOps recovery strategy.

B. Migration-level rollback — return to Helm
This procedure applies when the migration itself must be abandoned for a specific namespace.

Step

Recovery action

1

Declare migration rollback and block new releases

2

Disable Argo CD synchronization for the affected Application, accounting for any ApplicationSet control

3

Prevent destructive pruning/deletion and preserve live application resources

4

Capture the current live resource state, Argo CD manifests and event logs

5

Compare live configuration with the saved pre-migration Helm baseline

6

The Helm fallback is not guaranteed to be a one-command helm rollback. Argo CD-managed changes may not exist in Helm release history, and Helm metadata must be checked before any Helm upgrade or rollback. The pilot must prove this fallback procedure before it is accepted as production-ready.

Never use helm uninstall, destructive prune, or Application deletion with a cascading finalizer as an improvised rollback. Stateful resources, PVCs and shared routing objects require explicit protection.

Management-facing proposal
Proposal: Migration of Helm-Based Kubernetes Deployments to Argo CD GitOps
Proposed Timeline: 12 October 2026 – 1 January 2027
Duration: 12 weeks, with an additional two-week contingency
Scope: DEV, DEVB, DEVC, INTG, INTGB, INTGC, ACCP, PROD and DR

Objective
We propose migrating the existing Jenkins-driven Helm deployment mechanism to an Argo CD-based GitOps deployment model across our AWS EKS environments.

The migration will retain existing Helm charts and Jenkins CI pipelines while introducing Argo CD for declarative deployments, improved configuration traceability, continuous reconciliation and deployment visibility.

Implementation Strategy
The migration will follow a phased, namespace-by-namespace approach to minimize operational risk.

We will first establish the Argo CD platform, integrate the existing Jenkins pipelines, and validate the migration process in a lower-risk development namespace.

After successful verification, migration will proceed sequentially across the remaining development namespaces, followed by integration, acceptance, production and disaster recovery.

Only one namespace will be migrated at a time within the active rollout sequence. Each namespace will undergo configuration verification, deployment testing, health monitoring and rollback validation before proceeding.

Proposed Milestones
Phase	Timeline	Deliverable
Assessment and architecture	Weeks 1–2	Scope, ownership assessment and approved design
Argo CD and Jenkins integration	Week 3	Operational GitOps platform
Development migration	Weeks 4–5	DEV, DEVB and DEVC completion
Integration migration	Weeks 6–7	INTG, INTGB and INTGC completion
Acceptance migration	Week 8	ACCP validation and production readiness
Production migration	Weeks 9–10	Controlled production rollout
Disaster recovery	Week 11	DR deployment and recovery validation
Final sign-off	Week 12	Documentation and handover
Rollback and Risk Mitigation
A validated rollback mechanism will be maintained throughout the migration.

For application deployment issues, the previously approved Git configuration will be restored and synchronized through Argo CD.

Where the migration itself causes problems, a separately tested recovery procedure will allow the affected namespace to return to the legacy Helm deployment process after Argo CD resource ownership has been safely disengaged.

We will not proceed to the next namespace or environment if unresolved critical issues remain.

Production migrations will occur only during approved change windows, with monitoring, smoke testing, rollback readiness and stakeholder authorization.

Expected Benefits
Standardized and auditable Kubernetes deployments.

Reduced dependence on direct Jenkins-to-cluster deployment access.

Better configuration consistency across environments.

Improved visibility into application synchronization and drift.

A repeatable deployment and recovery framework.

Minimal disruption to existing Jenkins build and Helm chart workflows.

Approval of the target GitOps architecture and initial development pilot.

Production and DR change windows, including any year-end change freezes.

Mandatory sign-off checkpoints before production progression.

Overall recommendation: Approve the project as a 12-week phased migration, but treat the end of Week 4 as the key re-baselining point. The first namespace will establish the actual Helm-to-Argo CD adoption complexity, Jenkins integration effort, validation duration and recovery behavior. Those measured results should determine whether the remaining namespace schedule is achievable without compromising production stability.
